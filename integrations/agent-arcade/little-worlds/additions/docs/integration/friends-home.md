# Open the same traveller from Friends

To pair an installed world, run `node scripts/configure-friends-world.ts --database PATH_TO_WORLD_SQLITE --friends-origin FRIENDS_ORIGIN --world-origin WORLD_ORIGIN` from its release folder. For a managed desktop use `--desktop-service PATH_TO_SERVICE_JSON` in place of `--friends-origin`. Its `origin` selects Friends and its `littleWorldsOrigin` selects the world when `--world-origin` is omitted. If both specify a world they must match. The installer can call the same command. The two public addresses are stored beside that database and used at every restart of the regular launcher. Keep this small configuration with the database. A standalone world needs neither address.

Alternatively deploy the world with `LITTLE_WORLDS_FRIENDS_ORIGIN` set to the exact trusted Friends service origin and `LITTLE_WORLDS_PUBLIC_ORIGIN` to this world's externally visible origin. Use HTTPS, or HTTP on loopback for development. On the Friends service, set `LITTLE_WORLDS_ORIGIN` to that same world origin. Keep both databases when upgrading. A separate Friends database has its own instance ID.

The desktop requests a one-time ticket for its signed-in account and configured world. Before opening any game page, it posts `{ticket,expectedAccount}` to `/api/friends-session` using that account’s world cookie partition. The world redeems the ticket directly at its configured Friends service (`POST /api/v1/world-session-ticket/redeem`, body `{ticket,worldOrigin}`). Redemption yields the verified account, Friends instance UUID, world origin and optional verified legacy resident source and planet. A successful exchange returns `{ok:true,account}`. Each new device receives its own HttpOnly cookie for the same saved player. Stop at a failed exchange so visiting the standalone start page cannot create a different traveller by mistake.

For an older save, the original world cookie proves its owner's identity. A clean device can also recover the traveller if Friends independently confirms the old account's source and planet and the world still records that exact owner and source. If only an old client-supplied account label survives, first open the world from its original profile. A conflict leaves the existing cookie, player and house in place. Old standalone worlds continue to accept their own cookies.

When an owner allows friends to visit, the Friends backend requests `POST /api/friends-home` with its own fresh ticket and expected account. The world returns `{ok:true,account,planetId}` from the currently bound player's owned garden, or null for the planet ID if none exists. This lookup also works with zero residents and an offline owner after the verified destination has been saved by Friends. Friends enforces the owner's sharing choice and current friendship on subsequent visits. Resident activity still comes from the publisher.

From the world root, run `node scripts/build-worker.ts` and `node scripts/verify-friends-world.mjs`. An optional first argument selects a separate old world checkout (including its worker build and dependencies) to create the pre-upgrade database. The replay uses loopback, a temporary SQLite database and an isolated Friends ticket responder.
An active visitor's world client rechecks Friends sharing using a separate read-only capability obtained when the world redeems its normal session ticket. The capability is scoped to the signed-in Friends session and the configured world. The world keeps it server-side and checks the owner's current sharing choice and the current friendship before serving the roster or portrait bytes. The liveness of the owner's app does not affect this policy. A closed visit clears companion activity and offers Return to chat in a compatible desktop. It does not move the player or send a draft. The roster never uses an old authorization when Friends cannot confirm the check.

Deploy the Friends service and world updates together. A visit created by an older world session shows a prompt to return to the original chat and reopen the same planet to establish its scoped check. An already loaded earlier page needs a reload to show that prompt. Desktop versions with the new return handler show the in-world action. Older desktops retain their existing Return to messages button.
