# 一个 CLI / 同一模型，多个独立成员

中文 | [English](single-cli-team.en.md)

**只接好一种 CLI，或在 DSH 配好一个模型，就可以创建一支团队。** 不必先安装多家 CLI，也不必为每个成员安装一份相同程序。

比如三个成员都使用同一个 DeepSeek：

| 成员名 | 人设中的职责 | 使用的模型 |
| --- | --- | --- |
| 肥鱼甲 | 规划任务、分工、汇总结果 | 同一个 DeepSeek |
| 肥鱼乙 | 根据任务实现，并报告改动与验证 | 同一个 DeepSeek |
| 肥鱼丙 | 检查结果、指出遗漏、报告验证证据 | 同一个 DeepSeek |

也可以创建三个 Codex 成员，全部选择同一套已安装的 Codex CLI。成员的区别由名字、人设和各自的会话建立，不要求底层模型不同。

## 先选入口

| 你已有的环境 | 从哪里添加 | 需要准备什么 |
| --- | --- | --- |
| DSH，已配置可用的 DeepSeek | DSH 网页「频道」→「添加成员」→「DSH 模型」 | 三个不同成员名，选择同一个模型；无需 Discord 机器人 |
| DSH，想让多个 Codex / Claude Code / Gemini 成员协作 | 同一入口，类型选「本机 CLI」 | 在运行 DSH 的机器上安装并配置好所选 CLI；可重复选择同一种 |
| Discord | bothouse 安装向导，为每个机器人选择 CLI | 每个角色一个不同的 Discord 机器人 token；CLI 可以相同 |
| 自建平台（cloud_web） | bothouse 安装向导 → 自建平台 | 每个角色一个不同名字；无需 Discord token，CLI 可以相同 |
| 飞书 | bothouse 安装向导 → 飞书 | 当前向导支持单角色，不作为这份多成员教程的入口 |

首次安装 DSH 插件见 [上手指南的 DSH 入口](GETTING_STARTED.md#dsh-频道实验)。Discord / 自建平台见[接入指南](connect-discord-feishu.md)。DSH 模型成员直接使用 DSH 配置的模型；“DeepSeek”在这里指模型，不是要求安装一个名为 DeepSeek 的 CLI。

## 在 DSH 里创建三个成员

1. 打开 DSH 网页的「频道」，选一个聊天频道。先确保 DSH 已配置可用的 DeepSeek 模型；列表里没有时，先完成模型配置。
2. 在成员栏点「添加成员」，名字填 `肥鱼甲`，成员类型选「DSH 模型」，模型明确选一个可用的 DeepSeek，人设填写“负责规划任务、分工和汇总结果”，保存。
3. 再添加 `肥鱼乙`、`肥鱼丙`，选择**同一个提供方和模型**，分别填写实现、检查的职责。名字不能重复或带空格；相同模型可以重复选择。
4. 在成员栏的「主角色」中选择 `肥鱼甲`，把当前频道的「派活方式」选为「完全团队」。模型是否相同不影响这个选择。
5. 先分别 @ 三位成员确认能回复，再让甲把任务交给乙和丙。例如：

   ```text
   @肥鱼甲 请组织乙和丙合作写一份待办清单页面的方案。乙列出页面与交互，丙检查遗漏，由你汇总；先只讨论方案，不修改文件。
   ```

成员设置会保存，刷新网页不需要重建。它们通过公共频道里的消息交接，并不会因为选了同一个模型就共用一条对话。

选择「跟随 DSH 默认模型」时，成员在首次请求前确定默认模型，之后保留该会话自己的选择；这不等于所有已存在会话实时跟随全局默认模型。要确保三位成员用的是同一模型，就在创建时明确选择同一个提供方和模型。

### 改用多个 Codex 成员

仍从「添加成员」开始，成员类型改成「本机 CLI」，每次都选择 Codex，分别填写名字和人设。模型和登录使用该 CLI 在宿主机上的配置；这个表单不会为 CLI 成员设置 DSH 模型。Claude Code、Gemini 同理。

界面检测到 CLI，只说明找到了程序，不保证已登录、模型可用或 ACP 适配器启动成功。先让一个成员实际回复，再增加其他成员；程序只需安装一次，运行时会按成员建立实例，并按成员和频道维护会话。

### Discord / 自建平台的对应操作

Discord 向导用「再加一个机器人」增加角色，每个角色使用不同的机器人 token，在「本机 CLI」一步全部选择同一 CLI，再分别设置人设和主角色。不能把同一个 token 填三次当作三个成员。

自建平台向导按不同角色名添加成员，每个角色同样可以选择相同 CLI。同一平台上的同名角色再次配置会更新原角色，要增加成员就使用新名字。保存后按向导提示重启并逐一 @ 验证。

## 这和“单模型多进程”有什么区别

频道里的「派活方式」决定工作交给谁，不决定团队里能否出现相同模型：

| 派活方式 | 工作交给谁 | 三个肥鱼应该怎么选 |
| --- | --- | --- |
| 单模型多进程（solo） | 当前角色自己的子任务；能否开子任务取决于后端能力 | 不用于让三位常驻成员互相派活 |
| 完全团队（team） | 频道里的其他成员 | 适合三个同模型成员分工 |
| 混合（mixed，默认） | 频道成员或当前角色自己的子任务 | 同时需要两种方式时使用 |

添加成员得到的是常驻角色。子任务则由角色在执行任务时创建；选了 solo 并不会自动在成员栏生成另外两只肥鱼。

## 哪些独立，哪些共享

| 内容 | 当前行为 |
| --- | --- |
| 身份和人设 | 每个成员有自己的 ID、名字和人设。重复使用模型或 CLI 不会合并成员 |
| 对话上下文 | DSH 原生成员和本机 CLI 成员按“成员 × 频道”绑定独立会话。同一频道里的甲和乙不是同一 session；同一成员到另一个频道也另有会话 |
| 公共频道消息 | 成员被触发时会收到该频道相关历史；甲公开说出的内容可以成为乙的输入。这是协作所需的信息共享 |
| 私下的对话 | 系统不因使用相同模型就把甲的完整会话复制给乙。直接在会话发起的非频道轮次也不作为频道任务的回复自动发布，但成员以后仍可能在公开回答中引用自己已知的信息 |
| wiki / 长期记忆 | 会话和记忆不是一回事。启用的整理、检索或共享 wiki 可能把会话内容整理成其他角色能读到的材料；桥接向导还可能为角色配置自己的 wiki，需检查实际设置 |
| 文件和权限 | DSH 频道成员当前共用配置的工作目录。独立会话不等于独立文件、操作系统权限或私有频道访问控制；同时改代码仍要分工，必要时另行安排独立 checkout / worktree |
| 账号与额度 | 同一账号或 API 配置的调用仍受共同的计费、并发和限流约束；增加成员不增加账号额度，更多模型调用会产生更多用量 |

**不要把这项能力当作严格的保密隔离。** 需要保密的内容不能仅靠“不 @ 另一个成员”来保护，尤其不能先发到公共频道再要求其他成员不知道。

DSH 原生成员会话由插件管理，目前作为内部会话保留，不出现在普通 DSH 对话列表中。本指南不承诺每个成员都有可点击打开的独立私聊窗口，也不承诺成员级私有目录或私有频道权限已完成。

## 重置、恢复与最小检查

在 DSH 频道发送 `@肥鱼乙 /new`，会为乙在**当前频道**开始新会话，从这条命令之后继续读取频道消息；其他成员的会话不因此重置。旧频道消息和 wiki 不会被这条命令删除。仅改名字或人设不代表清空历史。

重启后的接续取决于后端的恢复能力：DSH 原生成员尝试恢复已绑定会话；本机 CLI 通过 ACP 恢复，不支持或恢复失败时会提示上下文丢失并新建会话，不保证永不丢失上下文。

首次配置可按下面的顺序检查，只用没有敏感信息的小任务：

1. 分别 @ 三位成员，让它们简述职责，确认三个身份各自回复。
2. 按上面的方案任务让主角色分工，检查频道里是否出现交接和汇总；只出现三个名字不等于已经完成协作。
3. 在测试频道对其中一位执行 `/new`，确认只收到该成员新会话的反馈，其他成员仍可继续原有任务。
4. 若要验收上下文绑定，核对本地存储中的成员/频道与 session ID，而不是根据模型是否猜中一句话判断；不需要公开完整会话日志。

这份清单提供检查方法；真实模型能否完成接力，需要在实际安装环境验证。开发者可查看 [DSH 成员实现](../dsh/collab/dsh-member.mjs)、[CLI 会话实现](../dsh/collab/cli-member.mjs)、[成员校验](../dsh/collab/roster.mjs)和[现有回归测试](../dsh/collab/collab.test.mjs)。

## 常见问题

- **只能选同一个模型一次吗？** 不是。名字和成员 ID 要唯一，模型和 CLI 可以相同。
- **成员栏找不到独立私聊？** 独立上下文已存在，但普通 DSH 对话列表不是频道成员的私聊入口；在频道点名交流。
- **成员不接力？** 先确认主角色、派活方式和 @ 名字。solo 不给其他成员派活；连续接力达到上限时，按频道提示由真人继续 @，不会无限自动互聊。
- **多开后变慢或报额度错误？** 检查共同后端的可用额度、并发限制和错误提示，不要反复创建成员来解决。
- **只有一个成员时也能用吗？** 可以。先跑通一个，再添加第二、第三位；无需一开始就配齐整个团队。
