# Codex exec 会话写入生命周期（#94）

2026-10-19：线上在 429 后重复报历史 stderr，积压消息连续遇到同一 thread 的 active writer 冲突。只读现场确认：桥接状态为空闲，但其 exec 子进程持有原 thread 写锁，且 rollout 仍增加事件。这里不能通过删除锁文件或新建会话恢复。

## 根因和边界

普通 exec 路径收到 turn.failed/turn.completed 就立即发终态，进程尚未退出；进程最终非零退出时又把累计 stderr 发成第二个错误。下一次 Send 没有等待前一个 reader，导致下一轮能在旧写入者仍存活时启动，且旧错误可被误归到下一条输入。

修复后文字与工具事件仍流式交付，成功/失败终态等 cmd.Wait 回收进程后才交付。同一适配器的 Send 串行启动并等待上轮 reader 清理；Close 取消等待并与 reader 注册同步。一轮结构化失败只交付一次；非零退出或缺失终态不能当成功；取消不会补发历史 stderr。严格语音恢复保留原 ID 核验。

本修复不改变供应商限流、WebSocket 协议或模型生成补丁的正确性，不自动重放失败输入，不改会话 ID。不同独立程序争用同一 thread 仍会由 Codex 原生锁拒绝，不能靠本适配器跨进程抢占。

## 验证与部署

exec_lifecycle_test.go 使用真实受控子进程复现终态先到、退出延迟、并发 Send、历史 stderr、缺失终态、非零退出和取消。旧实现回归红：提前终态、第二个写入者启动、无终态挂起、失败误判成功。修复后验证结果与部署记录以 #94 对应 PR 和统一运维交接为准。

发布前必须同时核对桥接忙闲和 Codex 实际写锁；旧版本的 busy=false 不能证明进程已结束。正常等待工作结束再重启，保留配置、会话映射、任务文件、日志和回滚二进制。真实供应商对话与故障后续聊需另行验收，模拟 CLI 测试不等于真人验收。
