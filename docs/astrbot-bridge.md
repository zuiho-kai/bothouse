# 外部聊天平台接入：AstrBot / QQ 群 ↔ bothouse 频道（社区方案）

> 状态：社区贡献（Refs #321）。本页只描述接入方式与注意事项，**不包含代码、具体网络地址或部署参数**。
> 参考实现由贡献者另行维护，不在本页范围内。

## 1. 目标与边界

很多用户已经在用 AstrBot / MaiBot 这类第三方聊天机器人管理 QQ / 微信群。本方案让这些群里的消息进入 **bothouse 自建频道（hub）**，频道的角色回复再回到原群。

当前描述的是 **L1 通道级接入**：

- ✅ 群消息 → hub 频道（以"用户"身份发一条消息）；
- ✅ hub 里角色的回复 → 原群 / 私聊；
- ❌ 还不是 L2"成员身份"（外部 bot 作为频道成员被 gate 路由、出现在成员列表）——后续阶段。

## 2. 链路

```
QQ / 微信 群
   │ (bot 被 @ 时收到消息)
   ▼
AstrBot 插件（外部平台侧，由贡献者维护）
   │ ① 以"用户"身份把消息写进 hub 频道
   ▼
bothouse hub（自建频道）
   │ gate 路由 → 角色（如频道主角色/子角色）回复
   ▼
② 客户端轮询 hub 的房间消息，取角色回复
   │ ③ 发回原会话
   ▼
QQ / 微信 群
```

## 3. 接入契约（复用现有 hub 能力）

- **鉴权**：使用 hub 的访问 token（由部署者在 hub 管理端生成），只保存在本机配置；
- **写消息**：以"用户"身份写入目标频道（复用 hub 已有的房间消息能力，不新增服务端接口）；
- **读回复**：按消息 id 增量读取房间消息，筛出角色身份的消息；
- **去重/游标**：客户端维护已读位置，断线重连后从该位置继续；注意"写消息"不应推进"读回复"的游标；
- **触发控制**：建议加触发前缀（例如 `/hub`），只转发需要的消息，避免打扰普通群聊；
- **防回环**：跳过 bot 自己发出的消息；外部平台侧转发后截断事件，避免与人格插件重复回复。

hub 的访问 token 只应保存在本机配置，不要提交到仓库或发到群里。

## 4. AstrBot 对接要点（v4 实测）

1. **事件优先级**：AstrBot 的消息处理器按 `priority` **从大到小**执行。若要让桥先拿到事件，优先级要高于其他人格/唤醒插件（实测需很高量级，具体以实际版本为准）。
2. **命令前缀会被吃掉**：消息开头的 `/` 可能被 AstrBot 当作命令前缀移除，`message_str` 可能不含开头的 `/`；前缀匹配要同时接受两种写法。
3. **发送 API**：`event.send()` 需要 `MessageChain`（由文本组件构成），直接传单个文本组件会报错。
4. **防重复回复**：桥转发后调用 `event.stop_event()`，避免同一条消息被其他人格插件再回一遍。

## 5. 隐私注意（重要）

bothouse 角色的回复可能附带 **reply footer**（模型/供应商列表、额度状态、本机工作目录）。对"对外"频道应关掉：

```toml
[[projects]]
  name = "role-1"
  reply_footer = false
  show_workdir_indicator = false
  show_quota_indicator = false
```

外部平台客户端也应再做一层清洗：

- 过滤 `*[...]` 形式的模型/额度尾注行；
- 过滤含 Windows 盘符与 Unix 风格家目录的路径行；
- 角色的过程消息（`第 N 步 · …`）不应转发到外部群。

## 6. 验证方式（贡献者本地）

- 用本地假 hub 对客户端做单元测试（不依赖 AstrBot、不依赖真实 hub），覆盖发送格式、只取角色回复、去重与游标、隐私清洗、鉴权错误不泄漏 token；
- 真实环境 e2e：QQ 官方机器人 + AstrBot + bothouse + 自建 hub，完成"群消息 → 频道 → 角色回复 → 回群"闭环；
- 验证内容不含任何凭据、群号或本机路径。

## 7. 已知限制与后续

- 只处理文本；图片/文件/卡片未接入；
- 客户端采用轮询读取（非推送）；
- 回复整轮一次性发回，非流式；
- L2 成员身份（外部 bot 作为频道成员、被 gate 路由）为后续独立工作，可能需要协议扩展或独立 Issue。
