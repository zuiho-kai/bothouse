# 发言权（Issue #33 第一步）

本步只增加离线调度：给定已经判定好的输入，决定这一轮谁可以回答。模块是 `companion/voice/floor.py`，回归在 `companion/tests/test_voice_floor.py`。它不调用伙伴、不识别语音、不播放音频，也还没有接到 `device_app`、讨论或任何正在运行的服务。

## 输入和输出

| 输入 | 含义 |
| --- | --- |
| 真人发言与轮次编号 | 一轮人类对话的身份。只能由真人显式动作构造，见下文。正文不参与点名或群体模式判断 |
| 是否点名、点名的是谁 | 由调用方显式传入。未点名时用当前设备绑定的伙伴 |
| 是否开启群体模式，以及来源 | 只有来源为真人显式开启才算数 |
| 伙伴状态 | 调用方给出的名单，不在这里发现伙伴。状态是 available、busy、unavailable |
| 当前设备绑定的伙伴 | 默认回答者 |
| 剩余预算 | 非负整数。本次还能授权几次伙伴调用 |

输出是一条决定：恰好一位回答者，或明确的“本轮没有回答者”及原因；是否还允许一次补充；一句可审查的原因。原因只陈述决定，不包含思维过程。`calls_authorized` 只计算这一次调用新授权的次数，重复事件为 0。

v1 的上限写在 `FloorLimits`：主回答者 1，补充 0 或 1，默认补充 1。调用点读这个配置，不另写一个散落的数字。

## 规则

- 默认只授权当前设备绑定的伙伴。其他伙伴不会被选为回答者。
- 用户点名一位伙伴时，只授权被点名的那位。当前设备伙伴不附带再答一次。
- 群体模式必须是真人显式开启。伙伴消息、引用、历史和定时消息即使带上群体标记，补充也不会开启。
- 群体模式开启后，主回答记入对话，才可以决定补充。补充最多一位、一次；也可以无人补充。决定之后不再改选，话语权的选择交还用户。
- 预算用尽、目标不可用、目标上一轮仍在收尾、名单里没有这位伙伴：本轮没有回答者，或补充不发生。不改叫下一位，不循环。busy 和 unavailable 的原因分开写：收尾中写「上一轮仍在收尾」，不写成「不可用」。
- 同一轮次编号、同一句话再次提交，沿用原决定，不再授权。判重只看这句话本身：正文、点名对象、群体模式及其来源、当前设备伙伴。预算、名单和忙闲变化不算另一句话。同一编号配上不同内容则拒绝，原决定保持不变。
- 停止或新的轮次编号会使旧世代失效。`is_current(turn_id, generation)` 以及纯函数 `reply_is_current` 只判断回复是否仍属于当前轮次。为假时不得播放、不得插入当前对话，也不得再授权补充。曾授权的正文仍写入共享记录，停止标成 stopped，被新问题取代标成 superseded；两者同时发生时标 superseded。

补充被接受之后，`speaker()` 改为那位补充者，表示此刻只授权这一位出声。无人补充不撤销已经授权的主回答。停止、被新问题取代，或本轮没有回答者时，`speaker()` 为空。

## 谁可以构造 HumanUtterance

任何新的 `HumanUtterance` 都会让当前轮次失效：`decide()` 收到新的轮次编号，就把上一轮标成已被取代，即使这次的结果是没有回答者。调用方因此只能在真人做出显式动作时构造它。

可以构造的动作：按住说话，确认发送。

不能用来构造的来源：声音活动检测，喇叭回声，伙伴消息。引用、历史和定时消息同样不能。这些信号即使听起来像一句新的人话，也不能另开轮次，也不能借此把正在播放或正在收尾的一轮标成过期。

点名和群体模式仍由调用方判定后传入。本模块不从正文推断。群体模式本身还要求来源是真人显式开启。

## 同一时刻只播放一位，是否意味着录音和请求也要全局互斥？

建议把两件事分开：播放继续全局互斥；录音和人类发起的新一轮，不要再被同一把房间锁一直挡到播完。

### 现在的代码在做什么

这是 #43 的房间占位，不是 #33 的发言权。`device_app.DeviceRoom` 用一个 `active` 槽，从接纳一直持有到生成收尾并且播放回执到达。两个设备页面共用这个槽。`/device/<id>/api/transcribe` 在 `room.active` 或 `service.transcribing` 时返回 409，提示等当前轮次结束再录音。因此 G哥 还在收尾播放时，Cursor 那台设备不能开始录音，新的请求也不会被接纳。忙时直接拒绝，不排队。

播放器侧，两页共用 `static/queue-player.js`，一次只顺序播放一路音频。讨论页同样要等播放完成或明确跳过才派下一位。这些约束解决的是“不要两路声音叠在一起”，以及“迟到的块不能在停止后接着播”。

### 建议

把两件事分开：

1. **播放继续全局互斥。** 同一时刻只出一路声音，对应 #33 的“只播放一位”，也对应硬件以后“转向正在说话的伙伴”。转向看 `speaker()`：默认是当前设备伙伴，点名后是被点名的伙伴，补充被接受后换成那位补充者。不要因为另一台设备正在录音，就让两位同时出声。
2. **录音和请求接纳按人类新轮次放行，不按“上一轮是否播完”一刀切。** #33 要求停止或新问题之后，旧轮次的回复不得插入当前对话，也不得再播放。用户要能在另一台设备上开始下一句；新轮次一旦被接纳，旧世代立刻 `is_current` 为假。随后返回的正文仍写入共享记录，并标成 superseded；不合成、不播放、不插入当前对话。停止则标成 stopped，同样只归档、不播放。已经送出的模型调用可以收尾，但不能借收尾再占用发言权。
3. **仍然要拒绝的是另一类重复。** 同一轮次的重复事件、预算用尽、伙伴不可用或上一轮仍在收尾，都不能再授权调用，也不能改叫下一位。群体模式之外不预留补充。这些限制防止循环接力，和“麦克风要不要等扬声器放完”不是同一把锁。
4. **单进程里的识别/合成容量另算。** 现在的 `service.transcribing` 避免两路识别同时挤进同一个 worker。集成时可以保留“一次只跑一路识别或一路合成”，这是管线容量。它不能再被解释成“G哥的播放没结束，Cursor 就不能形成新的人类轮次”。
5. **真机如果共用一只麦克风或一只扬声器，物理上仍然不能同时占用那只硬件。** 那是 #42 的设备能力。软件发言权不从“只播放一位”推出“两台设备的录音请求也必须全局互斥到播完”。

过期与否以轮次编号加世代编号为准，而不是只看房间槽是否还占着。集成时，播放、插入当前对话和硬件转向先问 `is_current`，或看 `review_reply` 的 `play` / `insert`。归档看 `review_reply` 的 `archive` 和 `mark`，不因过期跳过共享记录。这与现在的设备入口一致：停止或迟到的正文可以归档，只是不再合成、不再播放（见 [电脑设备](DESKTOP_DEVICES.md)）。停止把该世代关掉；新的人类轮次把旧世代标记为已被取代。两者都让旧回复失去当前播放和当前对话资格，正文仍留下。没有被本轮授权过的伙伴不写入这条归档。
