# 独立语音转发（#119，默认关闭）

当伙伴不能安全接续文字频道会话时，操作者可以明确选择独立语音会话。例如：肥鱼在开发频道运行长任务，设备闲聊只进入语音频道对应的独立上下文；不会向开发会话追加问题。
本实现是 #119 的传输与隔离部分，不做自然语言派活路由、进度查询或任务卡集成。

## 配置与归属

relay_project 放在 **8796 的可信 roles 文件**，不是板子请求或网关客户端提交的字段。
这是唯一选路点：8796 已负责设备认证、角色白名单、绑定核验、TTS 和播放回执，网关继续调用原 /turn。

~~~json
{"roles":[
  {"project":"voice-host","name":"语音入口"},
  {"project":"deep","name":"肥鱼","relay_project":"deep"},
  {"project":"grok","name":"Grok","relay_project":"grok"}
]}
~~~

以上只是示意。主配置的 project 是桥接已注册的来源项目，必须在名单中；session_key 明确指向「语音」频道。来源和目标项目都必须已在这个频道 /bind。原生后端、音色、设备授权仍按已有配置。

- 缺省/空字段：照旧走严格 /input；422 明确失败，**绝不自动降级**。
- 非空：提交前就选择 private relay，不先尝试严格路径，不把失败问题再投一次。
- 会话按来源项目、目标项目、完整来源 session_key（包括讨论串）、设备 ID 隔离；桌面入口用 desktop scope。
- 一条独立会话初次允许创建，以后只恢复保存的具体 native ID。身份丢失、改变或恢复失败都停止，需要人工核对。
- ACP 使用 session/load 或 session/resume；Antigravity 只接受 stream_json，发送前等待原生 init 确认 ID。旧纯文本后端不支持。
- 不根据“哪个频道忙”猜路由。不合并现有文字上下文，也不迁移已有普通 relay 会话。

## 本地协议

仍使用桥接现有 0600 Unix socket；不新增公网入口。

1. GET /relay/voice/binding?from=voice-host&to=deep&session_key=discord:CHANNEL&scope=DEVICE 核对绑定，返回稳定 relay_key 与 busy。
2. POST /relay/send，正文包含 mode: voice、上述身份字段、唯一 request_id 和 message。首次接纳202，相同ID/相同正文返回原回执，相同ID/不同正文409。
3. GET /relay/voice/REQUEST_ID 取 running / completed / failed 回执。只有 completed 的完整公开 text、匹配 relay_key/request_id/native ID 才进入已有 TTS。
4. POST /relay/voice/REQUEST_ID/cancel 尽力取消。取消不能撤销已经执行的工具；迟到正文不得再播。

桥接每条请求至多3分钟，沿用更短的既有 relay timeout。8796最长等待190秒；提交只POST一次，丢ACK只GET，不重新执行。
每次启动独立传入语音环境，不修改 Agent 的共享频道环境。ACP 的同步 Send 与事件读取并行，避免长答复和权限请求堵塞。
ACP 语音会话无论首轮还是恢复轮、普通 Send 还是 SendResumed，都只接受 stopReason=end_turn。截断、取消、拒绝、缺失或未知结束原因产生失败事件，不提供成功回执给 TTS。Antigravity 沿用其原生成功终态核验，不把 ACP 的字段套到其他协议。
POST 明确在接纳前失败时，503 正文带 submission=not_sent，companion 提示本轮未发送，不再轮询或取消。一般 5xx、断连、无法读取原回执时没有这项证明，继续只查询、不重发；不能仅凭 HTTP 503 声称没执行。

普通 /relay/send（不带 mode）行为保持；voice 不发 Discord 正文/工具日志、不自动批准权限、失败不把半截文本当成功。遇权限请求拒绝该轮，回到明确频道继续处理。
过滤仍依赖各后端现有公开事件边界；本改动不修复畸形私密标签。

## 持久化与限制

voice_relay.json 原子写入、权限0600，保存会话ID及结果回执。重启把未完成请求标为结果未知，不重放；损坏/写入失败时拒绝新输入。
只有当前进程确定尚未调用 Send 且没有保存原生 ID 的启动失败，才解除新会话的占位；失败请求仍保留去重回执。已有 ID 不清除，发送后的未知结果与崩溃留下的未知身份也不解锁。新的用户请求可以重试已确认未发送的启动失败，旧请求 ID 不重跑。
最多1024条回执，不自动淘汰去重证据；达到上限暂停接纳。清理/迁移策略尚待设计，不能直接删文件以“修复”会话绑定。
当前保存完整回答供确认与恢复，需按本地语音记录保护；不保存请求正文，只保存摘要。

这条路径暂时等完整回答才TTS，不享受 #132 的逐句模型输出播放。不能声称已解决 Grok 的首句延迟。

## 验证与晨间启用

合成后端测试覆盖：私密/工具事件不进入语音，幂等与冲突、线程/设备隔离、恢复失败不new、重启未知不重放、超时/取消/权限/错ID/空答复、阻塞Send、逐启动环境、Antigravity init确认。
Python覆盖绑定/回执校验、丢ACK只查一次提交、设备取消、复用TTS、明确拒收与未知503的区分；完整回归476通过、3跳过。
ACP 合成进程覆盖新建/恢复 × Send/SendResumed × 七种结束原因。普通 Send 的异常结束、启动失败永久锁定均已红绿复现；现有转发器首轮严格发送本来已能拒绝异常结束，本次把保证下沉到语音会话本身。
本机Go全量/race结果见PR验证栏。真实模型/设备语音未验收。

晨间先审批部署匹配的 bridge + companion，在隔离语音频道绑定来源/目标，选一个角色启用字段；测试两轮记忆、文字任务并行、停止、断连和错误退出思考状态。不要将验证消息投到正在编码的会话。
