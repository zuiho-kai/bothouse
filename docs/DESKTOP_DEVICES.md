# 电脑固定设备入口（Issue #43）

先验证“一位伙伴对应一台设备”的软件行为，再接两台实体终端。输入是设备页面确认的文字或录音转写，输出只属于该设备绑定的伙伴；反馈包括思考、分块播放、完整播放、停止与错误。电脑继续承担模型、ASR、TTS和共享记忆。

## 本次实现

- 首页展示明确配置的设备；每个 `/device/<device_id>` 只有一个固定伙伴，服务端拒绝改成别的 project。
- 复用 PR #47 的 DeviceRegistry/配置格式，以及现有 VoiceService、分块播放器和共享记录。一次输入只走一条 `/input` 链路，不再同时调用 DeviceRouter.converse，避免双重投递。
- 播放与录音分成两层（#33）：**播放全局互斥**，一台在出声时另一台的回答排队等这个槽；**录音和新问题按设备各自管**，只受这台设备自己未结束的轮次和“一次只跑一路识别/合成”的管线容量限制。**合成结束不等于播完**，播放槽保留到页面确认播完/停止/失败。同一台设备还有未结束的轮次时，新问题仍返回 409，不排队、不自动重试。
- 原会话在首次核对时固定；发送前、桥接接纳和返回时继续核对。改变绑定时拒绝，不能悄悄创建新会话。首版要求设备显式绑定同一个实例频道。
- 每个页面使用新的 client UUID，音频地址包含设备、轮次和该页面归属。其他设备、重复窗口、刷新后的新页面不能获取或重播旧音频。已完成/停止的音频不再提供重播，以免与下一位重叠。
- 停止先在浏览器暂停，再通知服务端。尚未送出的输入不再送；已经送达的 CLI 请求继续收尾，**这台设备**的槽位保留，迟到正文可归档但不会重新合成/播放。停止发生于分块合成中时，后续块不再发布。停止回执不等于释放：轮次快照的 `device_released` 为 false 时这台设备保持录音禁用并提示“后台收尾中”，收尾后才恢复，避免录完一句再被 `/transcribe` 409 拒绝。另一台设备的录音不受影响。服务日志行带时间戳，便于与共享记录事件对照。
- 共享 submitted/finished/playback 记录带 device_id/audio_target。语音使用原有隔离输出通道，不调用 Discord 发消息接口。同伙伴继续原会话，其他伙伴仍按需查共享记录。

## 启动与人工检查

先按 [独立实例配置](INSTANCE_SETUP.md) 准备 voice 配置和角色名单；设备格式参考 `companion/examples/device-bindings.json`，替换占位频道，保证设备与 voice 配置的 session_key 完全一致。

~~~sh
cd companion
uv run python -m voice.device_server \
  --config /absolute/path/to/device-voice-config.json \
  --roles /absolute/path/to/roles.json \
  --devices /absolute/path/to/device-bindings.json
~~~

三份文件与端口必须显式指定；voice 数据目录应独立，只有经过确认的桥接原会话和共享记忆目录共用。使用实际语音须安装语音额外依赖并提供本地模型，基础 uv 环境只承担离线测试。不会初始化旧配置、下载模型或启动 Discord bot。

1. 打开该端口的首页，分别打开 G哥和 Cursor 的设备入口。并排使用两个窗口；隐藏页面会停止该页面本轮，避免后台突然说话。
2. 向 G哥发送短问题。确认只有 G哥收到、只有 G哥页面播放，Cursor 保持安静。
3. G哥播放期间向 Cursor 提交：提示正在忙，保留输入；G哥完整播完后再提交，Cursor 才开始。
4. 在生成和播放中分别按“停止本轮”。声音立即停，迟到音频不恢复；后台请求仍在结束时，下一条暂不接纳。
5. 刷新或重复打开同一设备。新页面不能接管或自动重播旧回答。丢失停止回执时保持占位，需原页面确认停止，或确认设备已静音、后台任务已收尾后重启这个独立入口。
6. 真人按住录音、确认转写、听回答。自动浏览器使用文字和测试 WAV，不代替这一步，也不证明实体扬声器已经播放。

不要同时在旧8793与设备入口安排有声对话：房间占位只覆盖本设备服务进程，尚未提供跨服务/跨进程音频锁。8793普通页与讨论页的行为保持。

## 局域网设备接入（Issue #42）

默认仍只监听 `127.0.0.1`，电脑页面行为不变。要让外接终端走 Wi-Fi，必须显式给地址：

```sh
cd companion
uv run python -m voice.device_server \
  --config /absolute/path/to/device-voice-config.json \
  --roles /absolute/path/to/roles.json \
  --devices /absolute/path/to/device-bindings.json \
  --host 192.168.1.50
```

- `--host` 必须是本机实际网卡地址或 `0.0.0.0`；**非本机地址要求每台设备都有独立 `secret`**，缺一台就拒绝启动（不会降级成页面令牌）。
- 设备凭据写在 `devices.json` 的 `secret` 字段，32–128 位字母数字 `_` `-`，每台不同；格式见 `companion/examples/device-bindings-lan.example.json`。生成：`python3 -c "import secrets; print(secrets.token_urlsafe(32))"`。
- 设备请求带 `X-Device-Secret`。它只能访问 `/device/<自己的 id>/api/...`；拿别的设备的 secret 返回 403，未知设备也返回 403（不暴露设备是否存在）。
- **页面令牌不会发给非本机客户端**：远端 `GET /api/config` 返回 `token: ""` 和 `auth: "device-secret"`。HTML 页面、`/api/devices`、`/static` 只对本机开放，远端一律 403。
- `0.0.0.0` 无法固定 Host 头，此时 TrustedHost 放行任意 Host，唯一门槛就是设备凭据；能固定地址时优先写具体 IP。
- 配置文件含明文凭据，必须 0600 且不入库；`statuses()`、`/api/devices`、`/api/config` 都不会回显 secret。

仍是模拟测试：没有板上验证、没有 TLS。局域网明文 HTTP 只适合封闭测试网，正式演示要等传输加密那一项。

## 播放全局互斥，录音按设备各自管（#33 接入）

旧实现是 #43 的房间锁：`DeviceRoom.active` 只有一个槽，从接纳一直持到播完。它同时管住了播放、录音和接纳，结果是 G哥还在收尾时，Cursor 那台连录音都不行；用户录完一整句才收到 409。

现在拆成两层，`DeviceRoom` 里是两个字段：

| 层 | 字段 | 管什么 | 谁能占 |
| --- | --- | --- | --- |
| 播放 | `active` | 取音频、发播放回执、同一时刻只有一路声音 | 全局唯一，按接纳顺序交接 |
| 轮次 | `slots[device_id]` | 这台设备的录音、新问题、收尾 | 每台设备各自一个 |

- `/transcribe` 和 `/turn` 只看**本设备**的 `slots`。另一台在播或在收尾，都不再挡住这台设备录音；同一台设备自己还有未结束的轮次时仍然 409，不排队。
- 一次只跑一路识别和一路合成是**管线容量**（`service.transcribing`、`service.active`），不是房间锁；这时另一台会拿到明确的“另一台设备的回答还在生成，请稍后再问；本轮未发送。”，不会静默丢消息。`service.active` 要等整个 run 结束才清，CLI 生成和语音合成全部做完才算结束，**不是**开始播放就清。
- 因此按设备拆开以后，真正能并行的只有“**别人在播的时候我可以录音和提问**”。生成和合成仍然排队走同一条管线：B 的录音可以马上完成，但 B 的回答要等 A 的生成与合成结束；这不是 bug，是这台机器只有一路模型/合成容量。
- 播放槽按接纳顺序交接：前一轮播完、停止或失联释放后，最早等待的那一轮拿到声音。旧轮次不能靠迟到的回执把槽抢回去。
- 轮次快照新增 `playback_owner`（此刻在出声的设备）。`device_released` 与 `config.active_turn` 都变成**本设备**的含义，页面不再需要等另一台播完才放开麦克风。
- 发言权（`voice/floor.py`）按设备分开：`floors[device_id]`，世代编号也按设备各自计，`currents[device_id]` 只记本设备最近一轮。每次真人新轮次被接纳时先 `decide` 再 `_submit`：决定唯一回答者并让**本设备**上一轮不再是“当前轮次”。同一轮次编号重复提交是幂等重发，不会重新夺一次发言权。`decide` 返回没有回答者时直接 409，Bridge 一条输入都不会收到；`_submit` 失败则 `floor.stop` 掉这一代。
- 跨设备**不互相取代**：B 设备问新问题，不会把 A 设备已生成好、还没开播的回答判成过期。A 照样按接纳顺序播出，B 排在它后面等播放槽。
- 同一台设备内被新问题取代、又**还没开始播放**的回复：不播放、不进当前对话，正文仍写进共享记录并标成 `superseded`（`floor_review` 事件里 `mark=superseded`、`play=false`、`archive=true`）。用户已经停止的轮次保留 `stopped` 标记，不会被下一问改标成 `superseded`。
- **已经开始出声**的回复不被中途掐断：新问题排在它后面等播放槽，避免说到一半被打断；只在同一位伙伴内部才可能发生取代。

边界：这里的“按设备”是软件语义。真机如果共用一只麦克风或一只扬声器，物理上仍不能同时占用那件硬件；这属于 #42 的设备能力。跨进程、跨服务（例如 8793）没有共享播放锁，仍未解决。

## 失联租约（设备掉线后交还占位）

占位分成两个：**每台设备一个轮次槽**（录音、请求、收尾），**全局一个播放槽**。设备掉线时不能永远占着，但**沉默也不等于这一轮结束了**，所以租约只释放这台设备的槽和它持有的播放权，同时明确说明原因。

- 设备每 30 秒至少要有一次请求（`POST /device/<id>/api/heartbeat`，或任何查询/回执都算）。超过 30 秒没有任何动静，槽位释放。
- **播放中的回答不会被误释放**：收到 `playing` 回执时，服务端按“剩余播放时长 + 一个租期”把槽位保住，之后即使心跳丢一次也不会中途放开。页面在占着设备时每 10 秒发一次心跳；`static/app.js` 已内置。
- 续住有上限：单次回执最多按 10 分钟计算，伪造一个超大时长不能永久占住房间。
- 释放时该轮被标记为 `abandoned`，`abandon_reason` 写明“设备 N 秒没有心跳，占位已释放；本轮没有播放完成确认，后台任务仍会收尾”。**不会**被记成已播完，也不会被当成用户主动停止。
- 释放同时写一条 `lease_expired` 事件进共享记录（含轮次编号、设备、原因），事后可查，不是悄悄消失。
- `GET /device/<id>/api/config` 与心跳都返回 `lease`（`seconds`、`last_heartbeat_seconds`、`expires_in_seconds`）和 `last_release`，设备能自己知道还剩多久、上次为什么被释放。
- 释放只影响这台设备：另一台本来就能录音和提问，失联释放额外把它持有的播放槽交出来，排队中的回答得以出声；原设备回来后会看到自己的 `active_turn: null`、`available: true`，可以直接开新的一轮。
- 时长可用 `create_device_app(..., lease_seconds=...)` 调整，必须是正数；时钟可注入，测试用假时钟而不是真的等待。

边界：租约只看“有没有动静”，不能判断设备是真的断电还是在本地卡住；被释放那一轮的音频不会回收，只是不再允许播放。

## 圆屏页面入口（配合 #54）

页面必须和它调用的接口同源，否则从 `http.server` 或 `file://` 打开时 `/device/<id>/api/...` 一律跨域失败。

- 入口直接提供页面：`GET /device/<id>/screen`，资源走 `/device/<id>/screen/<path>`，和接口同一个 origin、同一个端口。
- 页面本身由 #54（大豆包）维护，构建产物放到 `companion/voice/static/screen/`（`index.html` + 资源）。目录可以用 `create_device_app(..., screen_dir=...)` 改。
- 服务端会在 `</head>` 前注入 `window.__COQIN_DEVICE__ = {"id": ..., "api": "/device/<id>/api"}`，页面不必自己拼设备编号。
- 没有安装页面时返回 404，并直接说明要把文件放到哪里；未知设备返回 404；`..` 之类的路径逃逸一律 404。
- 这个入口只对本机开放，远端拿不到页面（和 `/static` 一致）。

## 当前边界

本机页面是电脑模拟；`--host` 已支持局域网设备用每设备独立凭据接入，仍缺传输加密与固件。设备 UUID/client UUID 在本机是页面归属，远端由设备凭据认证。没有Wi-Fi实机传输、独立音频输出、设备状态灯或跨房间调度；发言权已按 #33 接入本入口（默认单人回应、播放全局互斥），跨进程调度仍未做。音频协议见 [DEVICE_TERMINAL.md](DEVICE_TERMINAL.md)。

未收到可信停止/播完回执时，不用超时猜测设备已静音；只有租约过期这一种超时会释放占位，而且会明确标记为 `abandoned` 并写明原因，不当作播放完成。不能检测被修改的客户端是否真的播放，也不保证用户听见。页面崩溃或停止回执丢失可能需要人工恢复；本进程最多保留200轮请求防重记录，达到上限要求空闲时重启。重启不会恢复旧音频或自动重发。

本次软件PR不关闭 #43，不等于真实双设备、真人麦克风或部署验收。生产8793/8787与Go桥接没有因本次开发而重启；上线另留独立记录。


### 客户端播放排队回归（#73）

回答状态 ready 只表示合成完成。没有 playback_allowed 且本轮尚未停止/释放时，普通设备页与圆屏显示“排队等待播放”，模拟终端保持 waiting；三个客户端继续查询原编号以续租，取得播放权后自动播放。不得在排队阶段猜音频地址、停止轮询或另发问题。停止和租约放弃仍终止本轮；等待超时不重发。

在 companion 目录运行：

~~~sh
uv run python -m pytest -q tests/test_voice_device_playback_queue.py
# 需要 Playwright 和本机 Chrome 或 Playwright Chromium；缺失会明确 skip。
# 使用当前 Python 环境安装 playwright 后运行：
python -m pytest -q tests/test_voice_device_queue_browser.py
~~~

浏览器用两个独立上下文，通过原生 HTTP 路由和真实媒体元素验证交接及排队停止，Bridge/TTS 为模拟实现。截图保存在 output/playwright/。这是软件回归证据，不代表真人语音或实体双设备验收。

混合入口用例另开三个上下文：A、B 使用普通设备页，C 使用圆屏。每页只提交一次，B/C 显示排队，客户端自身轮询驱动 A→B→C 自动接播；检查每位的 completed 回执先于下一位的 playing 回执，并确认之前的媒体已暂停。
