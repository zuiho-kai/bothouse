# 产品目标与验收

## 为什么做

用户需要的是能够连续交流、共同做事的伙伴。增加模型数量、聊天条数或设备数量都不是目的；每一阶段都要证明上下文接续、实际产物或使用体验有所改善。

共栖的交付形态是**一位 AI 对应一台独立实体设备**，让用户能辨认正在交流的伙伴。首个完整展示为 **G哥和 Cursor 两台设备，由电脑运行 AI、语音处理、记忆与任务执行**；Discord 延续文字交流，GitHub 承载可审查的项目成果。电脑原型与逐台调试是阶段证据，完整产品验收以 [Issue #8](https://github.com/Zssan12/conest/issues/8) 为准。

## 最终目标

1. 在 Discord 交代任务，换到电脑或外接语音设备后，同一伙伴知道刚才的约定并能继续执行。
2. 其他伙伴需要相关背景时，读取有来源的共享记录；语音正文不重复推送到 Discord。
3. 用户提出真实项目后，伙伴交付能审查的文件、测试和 PR。仅本次真人明确授权时使用原生子 Agent，默认自己完成。
4. 伙伴定期探索、交流并留下实际发现。用户每天看到发生过什么、形成了什么作品、哪些任务失败以及下一步。
5. 首个实体展示交付两台独立设备，每台固定对应一位伙伴；能持续对话、受控轮流、停止、接续记忆，并通过语音交代与查询一个实际任务。首版依赖电脑，设备负责收音、播放和状态反馈；具体板型、连接、供电与外观在硬件任务中确定，采购需用户确认。

以上采用 2026-10-17 已确认的产品定义，替代此前“单 AI 实体优先”和“单设备切换或多设备映射待定”的方案。首版可按键说话、显式召集、限制讨论轮数；自由接话、唤醒词和全双工不是首个展示的前置。

## 可观察的完成标准

| 场景 | 输入 | 必须看到的输出与反馈 |
| --- | --- | --- |
| 会话连续 | Discord 约定一件事，再从语音追问 | 原伙伴准确接续；原会话证据可核对；恢复失败明确报错 |
| 共享记忆 | 语音给出一项信息，让另一伙伴按需查阅 | 有来源和时间的记录；另一伙伴正确引用；Discord 没有重复正文 |
| 项目协作 | 一个限定范围的真实任务与验收条件 | Issue → 分支 → PR → 测试/审核；失败明确保留；没有越权或互相覆盖 |
| 子 Agent | 依次给普通任务、明确授权任务、普通任务 | 只有中间任务可派生；结果经过父 Agent 验收；结束后回收 |
| 每日日志 | 一天的真实活动与错误 | 日志可追溯；无活动/限额/失败如实展示；不把计划冒充成果 |
| 硬件展示 | 分别向 G哥、Cursor 的两台设备提问，明确召集讨论或交代小任务 | 各自设备播放对应伙伴的回答，同时只一位发声，可停止；原会话与共享记忆正确，工作成果可查看，断线和失败明确 |

语音的主观自然度由真人试听反馈；先测各阶段延迟，再根据测量选优化目标。尚无承诺的延迟 SLA。

## 推进顺序

- 电脑基础：沿用已有语音、共享记忆和 Issue/PR 工作流；补足当前版本真人录音验收，按 #43/#2 验证固定设备身份、原会话绑定、音频归属及独立配置。
- 实体接入：按 #42 确定接口和硬件方案，确认采购后逐台打通收音、播放与状态，再验证两台同时在线。
- 完整演示：按 #33/#44 验证受控讨论、停止、语音下达小任务与成果查询，复用 #6 的项目交付流程；两台设备一起按 #8 验收。
- 持续迭代：根据实际体验改进延迟、按需接话、长期记忆和共学；每日日志及各后端能力继续按各自 Issue 验收，不扩大首个展示的前置范围。

“涌现”是长期观察项：记录伙伴是否基于别人的发现改变行动、形成共同产物。调度与提示只能创造条件，不能保证该结果。

## 当前不承诺

完全自治的软件团队、自动文件锁/合并、任意后端可靠派工、所有角色语音、多人同时通话、硬件已量产，以及克隆即可启动六个 bot。
