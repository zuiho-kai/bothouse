# 公开进展与任务卡（#159，关联 #113）

机器人接受多步骤任务后，用专用公开报告通道写出开始、进展、关键发现、等待决定和结果。Discord 原地更新任务卡；开始、关键发现、等待决定、结果和异常追加到关联讨论串。普通更新不刷屏。Thinking、工具输入/输出和完整对话不进入这个通道。

主角色手动交接如何读取这些持久记录见[主角色手动交接](LEAD_HANDOFF.md)。

Grok 与肥鱼共用 ACP 入口，大豆包使用 Antigravity；三者都收到当前轮次的命令说明，通过已有 shell 工具调用同一个本地 API。没有按模型名提取“思考”，也没有修改 thinking_messages。是否按时报告仍取决于模型遵循公开进展提示，不能把协议测试当成三个真人频道验收。

## 启用

构建并部署包含本功能的 bridge 后，公开任务卡默认开启；如需显式关闭，在项目块加入：

~~~toml
[[projects]]
name = "已有项目名"
public_progress = false
# 保留现有 agent/platform 配置

[projects.display]
thinking_messages = false
tool_messages = false
~~~

public_progress 默认开启；显式设为 false 后需要重启 bridge 才生效。主 bot 派工须先调用 `task assign --batch ... --ref <参照实现 文件:行>`（多人改同组文件时加 `--base <底分支>`；非代码活写 `--ref '无（新建）'`），缺 ref 会被拒收；首次登记自动创建分工卡，无需先上报 start；同批成员进入同一张卡。派工提示要求先登记，再通过 task relay 派发。任务卡只开在工作区（#453），任务归属（卡片、序号、结果、看门）留在来源工作区 A；成员要在同一聊天频道下的另一个工作区 B 执行时，`task assign --workspace <B>` 与对应的 `relay send --task ... --workspace <B>` 必须显式写同一个工作区：B 须与 A 属于同一聊天频道并已 claim、有空位（来源是聊天频道时照 #453 拒绝开卡），目标 bot 须在 A 和 B 都绑定；bridge 校验归属与占用后让成员在工作区会话里跑，成员报告凭证只在该工作区有效，结果仍回原任务卡。重启后工作区关系随卡片和 dispatch 回执恢复；同一 `--request-id` 重试不会重复执行，换工作区会被拒绝。普通聊天、定时器和其他 bot 的后台消息不会自动开卡；直接发 @ 文本不经过登记接口，不能保证开卡。只对实现 TaskCardPublisher 的平台生效；目前是 Discord。机器人需要当前频道的读历史、发消息、嵌入链接和创建/发送公开讨论串能力；已在讨论串内时直接在那里留痕。缺权限时本地保留待投递记录并记录错误，不给它增加管理员权限。

每个真正进入执行的真人请求得到独立临时 run token，包括排队和本地语音续接。普通聊天不会开卡；模型接受多步骤任务时自己报告 start，模型没开卡时 bridge 按下节规则自动开一张。此版本不向其他 bot 发来的请求注入开卡命令，避免后台闲聊开卡。它没有给任务授予新的工具权限。

提示会给出当前 bridge 可执行文件、项目、会话、data-dir 和 run 参数。例如：

~~~sh
cc-connect progress --run <当前提示中的run> --seq 1 --kind start --title '检查语音绑定' --message '先核对入口和配置。'
cc-connect progress --run <同一run> --seq 2 --kind milestone --message '发现显示角色和语音入口不一致。'
cc-connect progress --run <同一run> --seq 3 --kind result --message '绑定已修正，真人语音待验证。'
~~~

project/session/data-dir 通常由命令提示显式指定；CLI 也兼容 CC_PROJECT、CC_SESSION_KEY 和既有 socket 路径解析。新任务 seq 从 1 连续增加，首次必须 start，标题最多 60 字符。续接旧任务使用提示给出的下一个 seq；序号随卡片累计，每轮仍最多 64 条，每条公开摘要最多 500 字符。其他 kind：update、waiting。相同序号与相同内容重试幂等；同序号改内容、跨项目/会话、旧 run、停止后的报告均拒绝。

CLI 的 recorded 回执表示本地持久化成功，不表示 Discord 已收到。失败时不重做原来的工具操作。不要报告凭据、推理草稿、原始工具日志或完整语音转写。

## 结束任务的子区自动归档

任务卡进入 `completed`（真人验收）、`failed` 或 `cancelled` 后，bridge 会在 `public_progress_thread_archive_mins` 配置的等待时间过去后归档它对应的 Discord 讨论串。`received`、`in_progress`、`waiting_user` 不归档。`result_ready`（已有结果、等真人验收）不是终态，另按 `public_progress_result_ready_archive_mins` 的等待时间处理；到点只归档讨论串、不改卡片状态：卡片仍是 `result_ready`，仍然可以验收。归档只是把讨论串收进 Discord 的“已归档”列表：消息、附件和卡片链接都保留，不删除任何内容；有人往讨论串发新消息时，Discord 会自动重新展开。创建任务子区时 `auto_archive_duration` 传 10080 分钟（Discord 允许的最大值，7 天），高于下面两项扫描等待，Discord 不会在 bridge 扫描前先把子区自动收起；实际归档时间由两项配置决定。

配置写在项目块：

~~~toml
[[projects]]
name = "已有项目名"
public_progress_thread_archive_mins = 1440          # 终态卡
public_progress_result_ready_archive_mins = 4320     # result_ready 卡
# 两项都写 0 = 分别关闭对应的自动归档
~~~

终态默认 1440 分钟（24 小时），沿用本 PR 之前的等待时间。`result_ready` 默认 4320 分钟（3 天）。来源：C酱 在 PR #498 的审核建议——主 bot 很少走验收这一步，这些卡若沿用 24 小时，子区数量基本降不下来。两项等待时间都从卡片最近一次更新时间和子区最近活动（最后一条消息或重新展开时间）中较晚者算起；有人刚回复或刚展开的讨论不会被同一轮收起。bridge 重启后会从 data_dir 里的任务记录恢复扫描，已有历史卡也按同一规则处理。

只归档 bridge 为任务卡创建的子区；如果卡片本来就在用户自己的讨论串里（`ThreadID == ChannelID`），不会归档。归档前要求卡片和最后一条公开事实已经投递完成，避免把最后一条消息挡在归档后。成功归档会写 `thread_archived_at`，之后扫描不重复调用；失败只记日志并在下一轮重试，不删除、不改任务状态（包括 `result_ready` 状态）。归档后如果又产生需要投递的关键事实（例如验收），bridge 先展开子区再投递，成功后清掉 `thread_archived_at`，让子区按新活动重新计时。改标题不会为了改名展开已归档子区；已归档子区的标题保持不变。机器人需要“管理讨论串”权限，缺权限时归档会失败并重试，不影响任务卡本身。

## 自动开卡

只在工作区频道（团队工作区登记表里记录的频道）自动开卡；普通聊天频道、私聊和语音回合一律不自动开，免得卡片占满聊天频道。模型自己用 progress start 开的卡不受影响，任何频道照常。

模型没调用 progress 也能看到进度：在工作区频道里，一轮里调用了 2 次非进度工具，或这一轮满 1 分钟仍没结束（沿用团队状态栏的“真实工作”阈值），且模型本轮没有自己 start、没有续接旧卡、没有用 task assign 开分工卡时，bridge 自动开一张卡。

- 标题取用户发的原话（与频道任务栏、团队状态同源，截到 60 字符），不含 bridge 拼给模型的补漏消息、@ 提醒、插话说明等提示块；纯图片等无文字请求用“处理中的任务”。不调用模型，也不公开工具名或参数。
- 命令行里带本轮 run token 的工具调用（progress、task assign、relay send）不计数；出现过一次后本轮不再自动开卡。
- 自动卡不占模型的序号：模型之后照常 `--seq 1 --kind start` 会落到同一张卡上，标题换成模型给的，Discord 原地编辑，不多发一张；直接 `--seq 1 --kind update` 也落在这张卡上。
- 自动卡先开、模型随后续接旧卡或把本轮活派到分工卡时，自动卡收为“已取消”，并写明已并入哪张卡。
- 回合结束沿用普通收尾：成功写“本轮已结束，结果见最终答复”，失败、中断、停止照旧。
- 自动卡不作为下一轮的续接候选（重启后也一样）；模型 start 接管后才按普通卡续接。
- 定时任务（cron、timer、heartbeat）和其他 bot 发来的回合不自动开卡，工作区里也一样；ws-handoff 叫醒工作区的那一轮（timer 带 `--handoff`）是交过来的活，照常自动开卡。
- 没有单独开关，随 `public_progress` 启停。

## 跨轮续接、查询和验收

同一会话最近的一张未验收卡，在上一轮结束且 24 小时内有更新时，可作为下一轮的续接候选。提示会提供卡片 ID 和下一个 seq；模型确认本轮继续同一件事后，以该 seq 上报 update，保留原卡和讨论串。新任务仍以 seq 1、kind start 开新卡。普通聊天和查询不会续卡；已取消、已验收或过期的卡不提供续接。当前只提供每会话一个候选，不支持按任意历史 ID 续接，也不根据聊天文字自动匹配任务。

本地命令可以查询和记录明确的真人验收：

~~~sh
cc-connect task list --data-dir /path/to/data --project fish --session 'discord:channel:user'
cc-connect task show --data-dir /path/to/data --project fish --id task-xxx
cc-connect task accept --data-dir /path/to/data --project fish --id task-xxx --by '确认验收的人'
~~~

list 默认查询整个项目最近 10 张卡，--session 可缩小到会话，--limit 范围 1～64。show 按 ID 返回公开任务记录，不包含模型推理或原始工具日志。它们走本地 Unix socket 的 GET /task；尚未新增 Discord 查询按钮或语音查询界面。

accept 走 POST /task/accept，只允许 result_ready / waiting_user；只有真人明确确认验收后才应调用。--by 是本地调用者填写的归属记录，**不验证身份，也不独立证明真人批准**，信任边界是本机 socket 的访问权限。成功后卡片变为 completed / verified，关键验收事实进入讨论串，并从置顶状态栏移除入口。这个终态不再被迟到的进展、回合结束、失败、停止或重启覆盖；旧卡验收不会清掉同会话新卡的续接候选。落盘失败返回错误并恢复原状态，重试必须真正落盘后才成功。

## 置顶状态栏里的任务入口

主 bot 维护每频道一张置顶团队状态栏，增加“待你处理”和“进行中”两组任务卡链接。只有已实际发布到该频道的卡片才进入列表；角色名称读团队配置。等待决定的任务排前面，同组按最近更新排序。普通更新原地编辑状态栏，不重复置顶每张任务卡。

沿用已有项目配置：

~~~toml
# 所有参与项目使用同一个 team_status_dir；保留现有角色名和其他配置。公开任务卡默认开启。
team_status_dir = "~/example-team"
team_name = "当前角色显示名"
# public_progress = false  # 如需关闭公开任务卡

# 仅主 bot 开启 team_status_inject。它可以汇总其他项目的任务卡，
# 不要求主 bot 自己也打开 public_progress。team_board 不写即开启。
team_status_inject = true
# team_board = false  # 如需关闭置顶状态栏
~~~

team_board 不写时对主 bot 默认开启（老配置升级后不改文件也会开启），写 team_board = false 关闭；非主 bot 忽略。它需要 team_status_dir 和主 bot 身份（team_status_inject 或 lead.json），不依赖 `setup lead install` 装的脚本。部署后的配置调整仍须单独授权；机器人需要在对应频道发布和置顶消息的权限。新状态栏置顶失败时保留消息 ID，下次重试同一条；编辑遇到网络或权限错误时不另发新卡，只有平台明确表示消息不存在才重建。已有状态栏在下次内容变化时检查并补置顶。

列表消费已有状态，不猜测任务是否成功：

- received / in_progress → 进行中；waiting_user → 待你处理。正常结束于 waiting 的轮次仍保留入口，重启也可恢复。
- result_ready / failed / cancelled / completed → 移出入口。原卡片、讨论串和持久化历史不删除；result_ready 仍是“已有结果 · 待验收”，不是主人已验收。
- 未结束的轮次在重启后按原协议标为中断，并移出入口；角色心跳超过一分钟不更新时不展示旧入口。
- 同轮或显式跨轮续接从 waiting 更新为 update/result，入口随之更新；真人验收后移出。另一项新任务不会自动解决旧卡上的等待事项。

只在原频道展示任务名称和链接，不把私聊、私密讨论串或其他频道的任务搬到公共频道。列表最多显示12项，并受消息长度约束；超过时注明剩余数量，完整卡片仍在各自频道。通常在团队状态轮询（2秒）和状态栏刷新（10秒）内更新，不每秒改消息。

## 状态和语音

- result 显示“已有结果 · 待验收”，不会设置已合并、已部署或主人已验收。关键发现是机器人主动公开的摘要，不是独立审计结论。
- 正常回合结束且没有明确结果报告时，卡片只说“本轮已结束，结果见最终答复；验收尚未确认”。waiting 保留等待确认。
- 后端失败、停止或桥接重启会覆盖尚未验收的运行状态；此前已经报告的成果仍保留，同时显示中断信息。已验收的卡保持完成，不会自动重新执行任务。
- 中间进展不触发 TTS。明确的 result/waiting 报告用作该轮语音回执；最多 60 字符，过长时播报“请查看任务卡”的短句，避免截掉句末的限制或待办。没有明确回执的普通回答保留原行为。错误回合沿用现有失败协议。
- 语音正文仍不重复发到 Discord；仅主动报告的任务摘要可以进入卡片。长篇最终答复继续保留在原会话历史。

## 持久化与恢复

记录位置：data_dir/public-progress/<项目名哈希>/task-*.json，文件权限 0600。只存任务身份、主动公开的摘要、平台映射、序号和投递位置；run token 不写入卡片或这些文件。token 仍会随提示进入对应 agent 原生会话历史，轮次结束即失效。

先落盘再确认，后台更新卡片并补送关键事件。网络调用有期限；投递重试不会调用模型。重启时把未结束的运行记为中断，只恢复投递。卡片及每条关键事件都有稳定标记；Discord 已成功接收但响应丢失时，通过机器人自身消息的标记恢复映射，避免再次创建。最多检查 2,000 条历史，不能确认是否已经发送时保留待处理并报错，不盲目补发。删除卡片、讨论串或撤销权限需要人工检查，不能保证在任意人工改动后仍自动恢复。

本地文件是该部署实例的单写者日志，不支持多个 bridge 进程共用同一项目日志目录。启用后，日志损坏或历史记录对应的平台被移除会使启动报错，需先检查日志和配置；不会静默丢弃记录。命令使用启动时解析的绝对 data-dir，避免 agent 切换工作目录后连错 socket。
