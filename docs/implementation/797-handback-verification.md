# 交回验收（#797）

## 生命周期
最终工作区报告成功送达聊天频道后，bridge 调用 board returned，保存 returned_at、reviewer，随后释放工作区。任务仍在 board.jsonl，只有 board done 表示验收完成。若工作区沿用旧习惯先写“已完成”再最终交回，收到报告时把未经验收的归档记录移回待验收。真正收口记录 review_accepted_at，延迟重复报告不得重开已验收任务。工作区释放不作为交回证据；释放且未完成的任务显示暂停。

新任务记录 dispatcher，交回后该原派活人负责验收。旧条目没有 dispatcher 时采用交接 Sender，最后才回退到处理交回的主角色。派活人暂时不在线时向当前主角色发一次接手提醒，保留原负责人，待角色恢复继续通知。

退回用 board reject 记录具体问题，再用 ws-handoff --resume 继续。优先认领原工作区；仅选择空闲且归本聊天频道或未认领的工作区，原区被占用则选择其他空闲区或排队。返工反馈不冒充用户答复。退回未恢复的任务保留可见，不自动归档。

## 提醒与恢复
复用已有工作区 watcher 与持久化 TimerStore，没有另建调度器。项目配置 team_review_after_seconds 调整超时门槛，默认沿用 teamTaskBoardStuckAfter 的一小时。

每次交回立即通知派活人；超过门槛只发一次超时提醒。整点按派活人及聊天频道合并待验收清单。已排队但尚未执行的阶段不再重复进入整点清单。首次恢复已超时任务只发超时阶段；过期整点清单和过时的首次提醒不会在重启后补发成批旧消息。执行及会话队列出队前重新核对任务身份，已验收/退回的条目从提示中去除。

旧数据只根据 team-exit-reported.json 的实际送达回执补建交回记录，并核对回执不早于当前绑定。单纯工作区释放或缺少回执不会被推断为验收待办。明确退回/暂停的条目不从旧回执复活。交回已送达但脚本写板失败时仍释放执行工作区，保留送达回执；脚本恢复后由既有 watcher 重试登记，避免脚本故障占住工作区。

内部生命周期命令和验收提示使用二进制附带的 collaboration/runtime 脚本，保留用户已安装或改过的 collaboration/lead。避免新二进制调用不支持 returned/reject 的旧脚本；运行时与原安装共享同一任务板和队列状态。

## 接口边界
待验收不占用工作区，但仍保持整个看板非完成状态（包括 cloud-web）。格式不合规的报告沿用现有提示重写流程，不凭模糊输出自动创建交回记录。PR625 也涉及报告投递路径，未在本件改动它；后续整合必须保留“投递成功 → 记录交回 → 释放工作区”的顺序，不能在投递失败时确认交回。
